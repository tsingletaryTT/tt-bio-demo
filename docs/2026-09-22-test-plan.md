# Test Plan — Adaptive Affinity Q&A (2026-09-22)

Working plan for exercising the generative-questions feature end to end once the
Tenstorrent chips are free. This is a scratch planning doc — **do not commit it**
(it is intentionally left untracked).

## What changed (the 4 tasks)

1. **Adaptive selector** — `ui/questioning.py::select_question()`: a pure function
   that picks the next question, preferring the on-screen target, then the
   least-recently-asked, with a no-immediate-repeat rule.
2. **Wiring** — `ui/app.py::_ask_next_question()` now calls that selector and
   tracks `_recently_asked`; it logs `attract loop asking <id> (target <id>)`.
3. **Catalog** — `playlist/questions.yaml` grew from 3 to 9 real, citable
   protein–ligand pairs (dhfr, trypsin, fkbp12, hsa). All `expected_s: null`
   until measured on hardware; the 6 curated ones carry a `source:` citation.
4. **End-to-end** — verify the adaptive questions actually fire in a live run.

The whole point of the hardware pass is to close the loop on the two things the
unit tests *cannot* prove: that a question's `expected_s` is real, and that the
attract loop actually asks the right question on the right screen.

---

## 0. Pre-flight — confirm the chips are actually free

The Qwen3.8-27B model was holding the chips. Before anything else, confirm it is
gone and the cards are idle.

```sh
# Which boards are present and what state they're in:
tt-smi -ls

# A full snapshot. tt-smi can dump JSON for machine reading — use that rather
# than the interactive TUI (which can hang when a card is mid-transaction):
tt-smi -s --snapshot_no_tty --offline
```

**Gate:** do not start the hardware tests until no process is holding a card.
If Qwen3.8-27B is still loaded, its workers will hold the devices and the
integration tests will hang in `futex_do_wait` (the same hang we hit). Confirm
the model is unloaded *and* that no stray worker process is still holding a
device before proceeding.

> If a card looks wedged from a previous run, do **not** reach for
> `tt-smi -r` — see CLAUDE.md. A leaked device handle from a crashed run is
> recovered by killing the holding process, not by a global reset.

## 1. No hardware needed — the new unit tests

These run under `venv-ui` (no chips required) and are the fast, repeatable
regression net for the selector logic and the catalog. Run them any time.

```sh
# Just the four files touched by this feature:
.venvs/venv-ui/bin/python3 -m pytest -v \
  tests/unit/test_questioning.py \
  tests/unit/test_app_questions.py \
  tests/unit/test_playlist.py \
  tests/unit/test_app_wiring.py

# Or the whole UI half (what CI's UI half runs):
.venvs/venv-ui/bin/python3 -m pytest tests/unit --ignore=tests/unit/runner
```

What each file pins down:

| File | Proves |
| --- | --- |
| `test_questioning.py` | The selector: on-screen target preferred, least-recently-asked ordering, no immediate repeat, tie-break by id, empty-pool safety. |
| `test_app_questions.py` | `_ask_next_question()` actually calls the selector and records the ask. |
| `test_playlist.py` | The 9-question catalog loads; the 6 curated entries carry a `source:` citation; a non-string `source` is rejected. |
| `test_app_wiring.py` | Narrowing the target selection still keeps the questions that cover it; the full target set is offered when nothing is narrowed. |

These are the ones to re-run on every edit to `ui/questioning.py`,
`ui/app.py`, or `playlist/questions.yaml`.

## 2. Hardware-gated — the integration suite

These open real Tenstorrent cards, so they are **opt-in** and must only run
when the chips are free (see §0). The wrapper handles the one non-obvious
constraint: `test_four_workers.py` must run in its **own** pytest process,
because a process that has opened a device cannot spawn a child that opens one.

```sh
# Everything, hardware included. This is the one command to run:
scripts/test.sh --hw

# Equivalent, via env var:
TT_BIO_DEMO_HW_TESTS=1 scripts/test.sh
```

`scripts/test.sh --hw` runs, in order:

1. `test_four_workers.py` in its **own** pytest process (it spawns 4 worker
   children; it must not share a process with the in-process device tests).
2. The rest of `tests/integration/` + `tests/unit/runner/` in a second process.
3. The full UI half.

It reports each half on its own line and only prints `OVERALL: PASS` if all of
them are green.

### Running the integration tests individually

Useful when bisecting. Run each in its **own** pytest invocation — in
particular, never share a process with `test_four_workers.py`:

```sh
V=.venvs/venv-runner/bin/python3

$V -m pytest tests/integration/test_affinity_real.py      -v   # real affinity scoring on-device
$V -m pytest tests/integration/test_real_fold.py          -v   # a real fold, end to end
$V -m pytest tests/integration/test_egg_on_device.py      -v   # fold + on-device check
$V -m pytest tests/integration/test_new_targets_timing.py -v   # fold timings for the new targets
$V -m pytest tests/integration/test_four_workers.py       -v   # MUST be alone in its process
```

`test_affinity_real.py` is the one most relevant to this feature: it is where a
measured affinity number would first be compared against a question's
`expected_s`. If a measured value lands here, that is the number to back-fill
into `playlist/questions.yaml` (replacing the `null`).

## 3. Manual / hands-on — the part only a human can sign off on

This is the part that matters most and that no test can fully stand in for:
watching the booth actually ask a sensible question about the protein on screen.

### 3a. Fast iteration (single target)

```sh
scripts/run-demo.sh --questions --targets trpcage --windowed
```

- `--targets trpcage` → one 20-residue target, ~4.4 s per fold, so the loop
  cycles quickly while you watch.
- `--windowed` → a normal window instead of fullscreen, so you can keep an
  editor/terminal next to it.
- `--questions` → opt in to the affinity Q&A feature (reserves one chip for it
  when 2+ chips are present).

### 3b. The full booth, as a visitor would see it

```sh
scripts/run-demo.sh --questions
```

Leave it alone. The attract loop is idle-gated:

- It arms after **60 s** with no input, then runs a 90 s cycle.
- The `ASK_QUESTION` cue fires ~82 s into that cycle, so the **first question
  appears roughly 2.5 minutes after the booth goes idle**.
- Note: the attract tick no-ops until there has been *at least one* input
  event (`_last_input_at` starts as `None`). So: touch it once, then walk away
  and let it sit.

### 3c. Live opt-in without a restart

In a running booth started *without* `--questions`, press **Ctrl+A** in the UI.
That exits with the sentinel code and `run-demo.sh` relaunches the booth with
`--questions` added — the operator path for enabling Q&A on the fly.

## 4. What to verify (checklist)

**Selector behaviour (watch the daemon log, or the on-screen question):**
- [ ] The question asked matches the protein **currently on screen** (the
      attract log line reads `attract loop asking <id> (target <id>)` and the
      target matches what's displayed).
- [ ] It does **not** ask the same question twice in a row.
- [ ] After cycling through a target's questions, it moves to the
      least-recently-asked one rather than repeating.
- [ ] When the on-screen target has no question of its own, it falls back to
      the general pool (and still doesn't immediately repeat).

**Content honesty (the hard constraint):**
- [ ] Every question shown maps to a **real, citable** protein–ligand pair.
- [ ] No question shows a fabricated binding time. Until a value is measured on
      hardware, `expected_s` stays `null` and the UI must not invent a number.
- [ ] The 6 curated questions each carry a `source:` citation in the YAML.

**End-to-end (hardware):**
- [ ] `scripts/test.sh --hw` reports `OVERALL: PASS` with the hardware line
      reading `INCLUDED (--hw)`, not `SKIPPED`.
- [ ] A real fold completes on-device and the on-screen fold time is sane.
- [ ] If a measured affinity value is obtained, it is written back into
      `playlist/questions.yaml` (replacing the `null`) and the citation updated.

**No regressions:**
- [ ] `scripts/test.sh` (no `--hw`) is still fully green — the software-only
      path must not have regressed.

## 5. Gotchas / cleanup

- **Chips busy = hang, not failure.** If an integration test hangs in
  `futex_do_wait`, the first thing to check is whether another process (a
  leftover worker, or a not-fully-unloaded model) still holds a card. Kill the
  holder; do not reset the card.
- **`test_four_workers.py` is process-sensitive.** Always give it its own
  pytest process. Running it in the same process as an in-process device test
  wedges all four workers.
- **Don't commit this file.** It's a working plan, not a deliverable.
- When done, if any `expected_s` was measured, that's the one durable change
  worth committing (along with its citation) — the plan doc itself should not
  be committed.
