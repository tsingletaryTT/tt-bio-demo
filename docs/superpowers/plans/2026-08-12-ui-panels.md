# tt-bio-demo Phase 3b: UI Panels and the Booth Loop — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the working renderer into a booth: telemetry, pipeline progress, a gallery a visitor can touch, and a four-state loop that resets itself after every visitor.

**Architecture:** All of this lives in the UI process (`.venvs/venv-ui`), consuming protocol events the daemon already emits. `ui/app.py` grows a state machine and is split; new widgets are separate modules with no GTK-independent logic mixed in, so their behavior is testable headlessly.

**Tech Stack:** Python 3.12, GTK 4.14 via PyGObject, `tt-smi` for telemetry, the project's own `protocol/events.py`.

**Spec:** [`../specs/2026-08-10-tt-bio-demo-design.md`](../specs/2026-08-10-tt-bio-demo-design.md) — §2 (components), §5 (interaction model), §6 (failure handling).
**Read before starting:** [`../../followups.md`](../../followups.md). Two entries there block this phase, and its last two sections are the lessons Phase 3a paid for.

## How this plan differs, and why

Phase 3a's review loop found **nineteen defects in the plan's own reference code**, which implementers faithfully transcribed. Its whole-branch review then mutation-tested the suite and found **13 of 15 mutations left it green** — the code was largely right, the evidence was not.

So this plan puts its precision where it belongs:

- **The tests are the specification.** They are given in full. Where the implementation follows from them, this plan gives structure and constraints rather than code to copy — you are expected to write it, not transcribe it.
- **Every test names the mutation it must catch.** Before you mark a task done, apply that mutation, watch the test go red, revert, watch it go green. Report both. A test that does not fail against its named mutation is not finished, regardless of what it asserts.
- **If a constraint here is wrong, say so.** Nineteen times an implementer's pushback was the thing that saved the build.

## Global Constraints

- **UI code runs under `.venvs/venv-ui/bin/python3`.** It has PyGObject, gemmi, PyOpenGL, numpy. It has **no torch and no tt-bio** — never import them here.
- Run the whole suite with `./scripts/test.sh`. UI-side tests go in `tests/unit/` (not `tests/unit/runner/`, which runs under the other venv).
- **Nothing in the UI may ever display a stack trace or raw error text.** Errors are logged; the display shows neutral copy.
- **An unhandled exception inside a GLib callback silently freezes that source forever** on this stack — worse than crashing, because nothing signals it. Every GLib-invoked callback carries a broad guard with the `return` outside the `try`. Preserve that shape in everything you add.
- **GTK only from the main loop.** The socket client's `on_event` fires on a background thread; marshal with `GLib.idle_add`.
- **The UI samples `tt-smi` itself**, not via the daemon. That duplication is deliberate: routing display data through the runner would couple the thing that must never fail to the thing most likely to. A wedged daemon must leave the silicon visibly breathing.
- **Brand colors:** dark base `#092221`, teal `#74C5DF`, accent `#1B8EB1`. pLDDT ramp `>90` `#0053D6`, `70–90` `#65CBF3`, `50–70` `#FFDB13`, `<50` `#FF7D45`.
- Real `tt-smi -s` shape, confirmed on this machine: `device_info[].board_info.{board_type,bus_id}` and `.telemetry.{asic_temperature,power,aiclk}`, values as strings sometimes leading-padded (`" 16.0"`).
- **Screenshots: use Spectacle.** `spectacle -b -n -f -o /tmp/shot.png` (background, no notification, fullscreen) produces a 1920×1080 PNG — verified. `grim` and wlr-screencopy do **not** work here; the compositor is KWin, not wlroots. This phase builds visible widgets, so capture them and look at the result rather than inferring appearance from state.
- Commit after every task with conventional-commit prefixes.

## File Structure

| File | Responsibility |
|---|---|
| `ui/telemetry.py` | Sample `tt-smi` on a timer in a background thread; expose the latest reading. No GTK. |
| `ui/panels.py` | The telemetry and pipeline widgets. Drawing only — no sampling, no event handling. |
| `ui/gallery.py` | The visitor pick grid, built from a playlist manifest. |
| `ui/playlist.py` | Load and validate `playlist/manifest.yaml`. Pure; no GTK. |
| `ui/states.py` | The four-state machine: transitions, the idle timer, and what each state shows. Pure — takes events and elapsed time, returns state. |
| `ui/app.py` | Wiring only: GTK application, window, and marshalling events into the state machine and widgets. |
| `ui/geometry.py` | Gains chain-aware splining (Task 3). |

Deliberate boundary: `telemetry.py`, `playlist.py` and `states.py` contain no GTK, so the booth's actual logic — when to change state, what a card's health is, which targets exist — is testable without a display. Only `panels.py`, `gallery.py` and `app.py` need GTK, and those are kept thin.

**Two deliberate deviations from the spec's §2 component table**, declared here so a reviewer judges them rather than reporting them as gaps:

- The spec lists `ui/pipeline.py` as its own module. This plan folds the pipeline widget into `ui/panels.py` alongside the telemetry widget, because both are thin drawing surfaces over pure helpers and separating them would produce two files of a dozen lines each. If either grows real logic, split it then.
- The spec does not name `ui/playlist.py` or `ui/states.py`. Both exist here because they are the parts worth testing without a display, and leaving them inside `app.py` is what would make the booth's behavior untestable.

**One integration seam to get right, called out because Phase 3a's worst bugs lived in seams like it:** Task 1 gives `DemoApp` a `display_state` so the preparing screen can ship before the state machine exists. Task 7 then introduces `StateMachine` with its own `preparing` state. **Task 9 must reconcile these into one source of truth** — almost certainly by making `display_state` a read-through to the machine — rather than leaving two places that can disagree about whether the booth is preparing. If you reach Task 9 and find yourself updating both, stop and collapse them.

### Task 2: Get `ribbon_from_cif` off the GTK main loop

**Files:** Modify `ui/app.py`, `ui/geometry.py`. Test: `tests/unit/test_ribbon_async.py`

**Why:** `docs/followups.md` measures it — **78 ms at 150 residues, 163 ms at 400, 407 ms at 1000, 1221 ms at 3000**. It runs inside a `GLib.idle_add` callback, so the whole UI — spin, cross-fade, telemetry — freezes for that long at exactly the reveal moment. Harmless against the 20-residue test target; not harmless against the playlist Phase 4 will bring.

**Produces:** ribbon construction happens off the main loop; the viewer is updated from the main loop only.

- [ ] **Step 1: Write the failing tests**

```python
import threading
import time

from ui.app import DemoApp


class _SlowGeometry:
    """Stands in for ribbon_from_cif, recording which thread called it."""

    def __init__(self, delay=0.3):
        self.delay = delay
        self.thread_name = None
        self.calls = 0

    def __call__(self, cif_path, **kw):
        self.thread_name = threading.current_thread().name
        self.calls += 1
        time.sleep(self.delay)
        return ("verts", "norms", "colors", "indices")


def test_ribbon_construction_does_not_run_on_the_calling_thread(monkeypatch):
    """The main loop must not be the thread that pays the 1.2s cost."""
    from ui import app as mod
    slow = _SlowGeometry()
    monkeypatch.setattr(mod, "ribbon_from_cif", slow)

    app = DemoApp(socket_path=None)
    app.viewer = _FakeViewer()
    caller = threading.current_thread().name
    app._handle_event({"type": "job_done", "job_id": "j1", "cif_path": "/tmp/x.cif",
                       "wall_s": 5.0, "mean_plddt": 95.0})
    _join_ribbon_worker(app, timeout=5.0)
    assert slow.thread_name is not None, "ribbon_from_cif was never called"
    assert slow.thread_name != caller


def test_the_viewer_is_updated_after_the_work_completes(monkeypatch):
    from ui import app as mod
    monkeypatch.setattr(mod, "ribbon_from_cif", _SlowGeometry(delay=0.05))
    app = DemoApp(socket_path=None)
    app.viewer = _FakeViewer()
    app._handle_event({"type": "job_done", "job_id": "j1", "cif_path": "/tmp/x.cif",
                       "wall_s": 5.0, "mean_plddt": 95.0})
    _join_ribbon_worker(app, timeout=5.0)
    app._drain_pending_ribbon()            # what the main loop would do
    assert app.viewer.ribbons == 1


def test_a_geometry_failure_leaves_the_previous_view_intact(monkeypatch):
    from ui import app as mod
    from ui.geometry import GeometryError

    def explode(cif_path, **kw):
        raise GeometryError("bad cif")

    monkeypatch.setattr(mod, "ribbon_from_cif", explode)
    app = DemoApp(socket_path=None)
    app.viewer = _FakeViewer()
    app._handle_event({"type": "job_done", "job_id": "j1", "cif_path": "/tmp/x.cif",
                       "wall_s": 5.0, "mean_plddt": 95.0})
    _join_ribbon_worker(app, timeout=5.0)
    app._drain_pending_ribbon()
    assert app.viewer.ribbons == 0
    assert app.viewer.cleared == 0, "a failed ribbon must not blank the screen"


def test_a_second_fold_supersedes_a_slow_first_one(monkeypatch):
    """Two folds in flight must not race to update the viewer out of order."""
    from ui import app as mod
    monkeypatch.setattr(mod, "ribbon_from_cif", _SlowGeometry(delay=0.2))
    app = DemoApp(socket_path=None)
    app.viewer = _FakeViewer()
    app._handle_event({"type": "job_done", "job_id": "j1", "cif_path": "/tmp/a.cif",
                       "wall_s": 5.0, "mean_plddt": 95.0})
    app._handle_event({"type": "job_done", "job_id": "j2", "cif_path": "/tmp/b.cif",
                       "wall_s": 5.0, "mean_plddt": 95.0})
    _join_ribbon_worker(app, timeout=10.0)
    app._drain_pending_ribbon()
    assert app.viewer.ribbons <= 1, "only the newest fold's ribbon should land"
```

### Task 4: Sample `tt-smi` from the UI

**Files:** Create `ui/telemetry.py`. Test: `tests/unit/test_ui_telemetry.py`

**Produces:** `TelemetrySampler(period_s=2.0, timeout_s=5.0)` with `.start()`, `.stop()`, `.latest() -> list[CardReading] | None`, `.age_s() -> float | None`; `CardReading(index, board_type, temperature_c, power_w, aiclk_mhz)`; `parse_snapshot(dict) -> list[CardReading]`.

### Task 7: The four-state machine

**Files:** Create `ui/states.py`. Test: `tests/unit/test_states.py`

**Produces:** `BoothState` (enum or str constants: `attract`, `gallery`, `folding`, `showcase`, `preparing`); `StateMachine(idle_timeout_s=45.0)` with `.on_event(event) -> BoothState`, `.on_touch() -> BoothState`, `.on_pick(target_id) -> BoothState`, `.tick(now) -> BoothState`, `.state`, `.selected_target`.

**Pure by construction** — it takes protocol events, touches and a clock reading, and returns state. No GTK, no timers of its own. That is what makes the booth's actual behavior testable.

- [ ] **Step 1: Write the failing tests**

```python
import pytest

from ui.states import StateMachine


def _sm(**kw):
    return StateMachine(idle_timeout_s=45.0, **kw)


def test_it_starts_in_attract():
    assert _sm().state == "attract"


def test_a_touch_opens_the_gallery():
    sm = _sm()
    assert sm.on_touch() == "gallery"


def test_a_pick_starts_folding_and_remembers_the_target():
    sm = _sm()
    sm.on_touch()
    assert sm.on_pick("hemoglobin") == "folding"
    assert sm.selected_target == "hemoglobin"


def test_job_done_moves_to_showcase():
    sm = _sm()
    sm.on_touch(); sm.on_pick("x")
    assert sm.on_event({"type": "job_done", "job_id": "j1"}) == "showcase"


def test_idle_returns_to_attract_from_every_interactive_state():
    for reach in (lambda s: s.on_touch(),
                  lambda s: (s.on_touch(), s.on_pick("x"))):
        sm = _sm()
        reach(sm)
        sm.tick(now=0.0)
        assert sm.tick(now=46.0) == "attract"


def test_the_idle_timer_resets_on_every_touch():
    """A visitor still interacting must not be timed out mid-browse."""
    sm = _sm()
    sm.on_touch()
    sm.tick(now=0.0)
    sm.tick(now=40.0)
    sm.on_touch()                       # still here
    assert sm.tick(now=50.0) != "attract"


def test_attract_does_not_time_out_to_itself_repeatedly():
    sm = _sm()
    sm.tick(now=0.0)
    assert sm.tick(now=1000.0) == "attract"


def test_a_fold_that_fails_does_not_strand_the_visitor_in_folding():
    sm = _sm()
    sm.on_touch(); sm.on_pick("x")
    assert sm.on_event({"type": "job_error", "job_id": "j1",
                        "target_id": "x", "message": "boom"}) != "folding"


def test_not_ready_overrides_whatever_the_visitor_was_doing():
    sm = _sm()
    sm.on_touch()
    assert sm.on_event({"type": "not_ready", "missing": ["x"]}) == "preparing"


def test_recovery_from_preparing_returns_to_attract_not_to_a_stale_gallery():
    sm = _sm()
    sm.on_touch()
    sm.on_event({"type": "not_ready", "missing": ["x"]})
    assert sm.on_event({"type": "job_start", "job_id": "j", "target_id": "t",
                        "model": "m", "card": 0, "n_residues": 20}) == "attract"


def test_an_attract_loop_fold_does_not_look_like_a_visitor_pick():
    """job_start with no pick outstanding is the attract loop, not a visitor."""
    sm = _sm()
    start = {"type": "job_start", "job_id": "j", "target_id": "t",
             "model": "m", "card": 0, "n_residues": 20}
    assert sm.on_event(start) == "attract"
    assert sm.selected_target is None
```

**Mutations these must catch:** a fixed idle deadline that ignores later touches (test 6 red); `job_error` leaving the state at `folding` (test 8 red); `not_ready` not overriding (test 9 red); recovery landing in `gallery` (test 10 red); attract-loop folds being treated as picks (test 11 red).

Test 11 is the subtle one. The daemon folds continuously; most `job_start` events are the attract loop, not a visitor. A state machine that treats every fold as a visitor interaction will never return to attract.

- [ ] **Step 2: Record two minutes of the booth running hands-off**

The deliverable is a **two-minute video of the demo running unattended on real
hardware** — nobody touching it, cards actually folding, the loop doing what it
will do at the conference. This is what gets shown to people who will not read
any of this.

Requirements for the capture:

- **Two minutes minimum, continuous, no cuts.** The point is that it runs by
  itself; an edited highlight reel proves nothing about that.
- **Real daemon, real cards.** Not the mock runner. Confirm folds are happening
  on silicon — `tt-smi` before and after, or the daemon log alongside.
- **Hands off for the whole recording.** No mouse, no keyboard, no interaction.
  If the attract loop is the only state reachable without a touchscreen, record
  that and say so; do not fake a visitor.
- The window should be full-screen or close to it, so the recording shows what a
  booth screen shows.

**Tooling note:** this machine's Spectacle is **23.08.5**, which is stills-only —
video recording arrived in Spectacle 24.02. So use `ffmpeg` (via the X11 display,
which is available) or OBS, both installed. `wf-recorder` will not work: it needs
wlroots and this compositor is KWin, the same reason `grim` fails. Verify your
capture actually plays and actually shows folds completing before declaring it
done — a two-minute recording of a frozen window would be a bleak artifact.

Save it somewhere durable and reference it from the report. Do not commit a large
binary to the repo without checking the size first; if it is more than a few tens
of megabytes, put it outside the repo and record the path.

## Definition of done

1. `./scripts/test.sh` passes both halves.
2. Every task's named mutations were verified red-then-green, with evidence in its report.
3. The booth cycles attract → gallery → folding → showcase → attract, driven by a real daemon.
4. Telemetry keeps updating after the daemon is killed.
5. A real fold's reveal does not freeze the UI.
6. A two-minute hands-off video exists showing the booth running on real hardware.

## What this phase deliberately leaves out

- **The curated playlist's content** — real targets, blurbs, pre-cached MSAs and thumbnails are Phase 4. This phase ships the machinery and one target.
- **`tools/make_thumbnails.py`** — Phase 4, alongside the art it generates.
- **Debian packaging and the systemd unit** — Phase 4.
- **Multi-card scheduling** — the daemon holds one card; `--device` was removed in Phase 3a and that stands.
- **Touchscreen input hardware** — the state machine takes touches; whether they arrive from a screen, a mouse or a keypress is a booth-setup decision.
