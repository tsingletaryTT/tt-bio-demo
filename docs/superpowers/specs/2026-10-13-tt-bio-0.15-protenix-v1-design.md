# tt-bio 0.15.2 upgrade and the move to protenix-v1

Date: 2026-10-13. Branch: `tt-bio-latest-upgrade`. Status: draft for review.

## Why

The booth pins tt-bio 0.12.0. Upstream is at 0.15.2. Between them, 0.13.0 stopped
downloading the Protenix-v2 weights: upstream's own Protenix-v2 release note says they may
not be redistributed without the rights holder's consent, and the Hugging Face repo that
0.12.0 fetched from answers HTTP 401 (checked 2026-10-13, unauthenticated). tt-bio's
registry now lists `protenix-v2` as `manual` with no source.

The booth folds with `protenix-v2`. A fresh source checkout or .deb install can no longer
fetch the checkpoint, and the .deb cannot ship it. This box still holds a copy at
`~/.boltz/protenix-v2.pt`, which loads, so nothing is broken here today. The turnkey
install is what is broken.

## Decision

Move the booth to **`protenix-v1`**, upstream's own v0.5.0 checkpoint. It is Apache-2.0
and downloads normally (`tt-bio weights --download protenix-v1`, 1.47 GB at `<cache>/protenix/model_v0.5.0.pt`, mirrored at
`moritztng/protenix-v0.5.0`). Protenix-v2 is not supported by the shipped booth. The local
v2 file is kept as a before/after reference for the measurement pass only.

## Does the project still have a reason to exist?

Yes. tt-bio 0.15.2 has no demo UI, viewer or dashboard. It has a terminal live display,
`predict --listen` (a job controller), and `msa-server`. Nothing overlaps the GTK booth, the
live diffusion trajectory, the gallery or the affinity Q&A.

## What is the same and what differs

Same, by tt-bio's own comment in `main.py`: one implementation, two checkpoints.
`tt_bio.protenix` reads c_z, block count and recycle count off the weights. `Protenix`,
`edm_sample(..., dump_fn=)` and the `_read_bio_chains` 5-tuple are shared. So the live
trajectory tap and the daemon's feature-building path should carry over unchanged.

Differs:

| | protenix-v2 | protenix-v1 |
|---|---|---|
| Pair width (c_z) | 256 | 128 |
| Trunk recycles | 10 | 4 |
| Templates | yes | none (unused here) |
| Weights | manual, not redistributable | downloads, Apache-2.0 |

Consequences for the booth, all to be measured and none assumed:

- Folds should be faster and the `trunk` stage shorter. `first_frame_s` and `expected_s`
  for every target change, so the per-target dwell caps move with them.
- pLDDT changes, because this is a different checkpoint. Every gallery claim that quotes a
  pLDDT or a structural property (the DNA duplex pairing, tRNA's ~124 degree corner,
  trypsin's low confidence) is re-checked against v1 output before it stays.
- The L1 clash that FKBP12+SB3 hit on 0.6.3 was shape-dependent. It may or may not recur.
- Weight download size falls from ~3.7 GB of fold weights to ~3.3 GB (1.47 GB checkpoint plus the 1.86 GB molecule library). The "6.9 GB" figure in
  docs, debconf text and the one-pager is re-derived, not edited by hand.

## Scope

1. **Pin** `TT_BIO_VERSION` 0.12.0 to 0.15.2. Metadata check first: `ttnn` pin and
   `requires-python` against the vendored SFPI toolchain.
2. **Model swap.** `runner/folder.py`, `queue.py`, `daemon.py` (advertised models),
   `preflight.py` (`MODEL`, fallback weights), `ui/playlist.py` (`DEFAULT_MODEL`), playlist
   YAML inputs that name a model, `scripts/make-thumbnails.py`, `scripts/doctor.sh`
   (checkpoint path becomes `protenix/model_v0.5.0.pt`, size floor re-derived from the real
   file), `scripts/setup-venvs.sh`, the weights postinst, `INSTALL.md`, README.
3. **Contract tests.** The tests that parse the pinned tt-bio's source for every printed
   `tt-bio weights` command keep working and are re-pointed at `protenix-v1`. The
   booth-agreement test (printed model equals the model the booth folds) must go red if
   either side still says v2.
4. **Re-measure** all seven targets on hardware under a gozer lease: three warm folds per
   target, cold fold discarded, same method as the 0.7.3 and 0.8.0 passes. Record
   `expected_s`, `first_frame_s`, max silence and the pLDDT band, then refresh the manifest,
   thumbnails, README, site cards and the one-pager (rebuild and look at the PDF).
5. **Site and README facts that go stale with a version bump**: commit counts (re-measure
   with the spec's `-i` method against the v0.15.2 tag, verify authorship before printing),
   model-family count, and any "as of v0.x" sentence.
6. **v2 reference run.** Fold the same seven targets with the local v2 file under 0.15.2,
   to report what the change did to times and pLDDT. This is a measurement only.

## Order of work

Spike first, because three things are unverified:

- `Protenix.load_from_checkpoint` accepts the v1 file and a real 200-step fold streams 30
  frames through the existing tap.
- The 0.15.2 API shapes `folder.py` and `daemon.py` rely on are unchanged. This has broken
  on two earlier bumps (0.7.0 `hf_artifact`, 0.8.0 the 4- to 5-tuple), and an import check
  does not prove a contract.
- `weights.fetch("protenix-v1", root=cache)` lands where `weights_cache()` and the doctor
  expect.

Then the swap, then the measurement pass, then copy.

## Considered and not adopted

- **`--write_pae` / full PAE matrix.** Real, and could drive an interface-confidence view,
  but it is a new feature with its own UI. Separate spec.
- **Boltz-2 per-step trajectory hook (0.13.0).** A possible second live-trajectory model.
  Separate spec; needs its own Boltz-2 weights and timing.
- **OpenDDE constraint guidance (0.15.1).** Antibody-specific, large and slow. No target on
  the playlist uses it.
- **`--diffusion_precision bf16`.** Upstream's 0.14.0 note says it picks a confidently
  wrong binding mode on 2 of 11 complexes. Not suitable for a booth that makes claims.
- **Speedups in 0.14.0 and 0.15.1.** Measured for 730-token folds. Our targets are 20 to
  585 residues. They arrive with the pin and are reported, not tuned for.
- **Supporting v2 as an opt-in.** Rejected: it would keep a model on the playlist whose
  weights a fresh install cannot get, and doubles the test matrix.

## Success criteria

- A fresh `setup-venvs.sh` run and the .deb install both end with every doctor box ticked
  and no manual weights step.
- A real fold of each shipped target completes on a chip under a lease, with a streamed
  trajectory.
- Every number and structural claim printed in the booth, README, site and one-pager is one
  that this branch measured on v1.
- The full suite is green with hardware skipped, then green with hardware on all chips.
- No remaining mention of `protenix-v2` outside history (CLAUDE.md log, dated specs, plans)
  and the explicit "v2 is not shipped" explanation.

## Risks

- v1 may change what a visitor sees: a shorter trunk means less of the "prior fold held
  dimmed" window, which is good, and lower or different pLDDT, which needs copy review.
- A target may fail on v1 as FKBP12 did on 0.6.3. A failing target is reported, not hidden,
  and the harness already records per-target errors instead of aborting.
- The JIT kernel cache is cold after the bump and after the model change. The first pass is
  discarded and the cold figure is recorded separately.
